# 效能基準

這份文件記錄**在同一台機器上量到的比例**，不是絕對值。

絕對的 TPS 取決於機器：開發筆電、CI runner、正式環境的數字互相沒有意義，
而把它們拿來比較會得出錯誤的結論。比例（A/B）在不同機器上大致穩定，
也正是容量規劃真正需要的輸入。

**這裡的數字不是 CI 門檻。** 共用 runner 的效能數字抖動很大（鄰居噪音、CPU
型號、磁碟）。一個會偶發失敗的效能門檻，最後會被加上 `continue-on-error`
或直接刪掉 —— 而那比沒有門檻更糟：它看起來還在守著。要變成門檻，
先要有同一台機器上的多次觀測。

## 稽核寫入放大（migration 049）

**問題**：049 把稽核擴大到 `work_orders` 與 `assets`，而稽核存的是
`before_data` 與 `after_data` **整列**（56／35 欄）。049 的檔頭說那是
「一筆真實的寫入放大」，並寫了「若日後真的太多，該做的是分割輪替策略」——
但沒有數字，所以無法回答「多少才算太多」。

**量法**：`make audit-overhead-bench`。唯一的變數是 `trg_audit` 的開關；
角色與情境兩次都相同（`fms_owner` + 平台情境），因此量到的是**稽核觸發器**
的成本，**不含 RLS 的成本**。

| | 吞吐 | 平均延遲 | 稽核列 |
|---|---|---|---|
| A：稽核開著（049 之後） | 6,275 tps | 0.637 ms | 1,000 |
| B：稽核關掉（049 之前） | 7,718 tps | 0.518 ms | 0 |
| **比例** | **81%** | **1.23 倍** | |

### 怎麼讀這個數字

**19% 的吞吐成本，換一份完整的欄位級稽核軌跡。** 以「誰在什麼時候把這張工單
的優先度改掉」現在答得出來而言，這是便宜的。

**因此目前不需要分割輪替策略。** 049 檔頭那個顧慮在這個量級上不成立。
真正會先撞到的是**儲存體**而不是寫入延遲：每次變更寫兩份完整的列，
`audit_log` 的成長速度大約是被稽核表變更量的兩倍以上。那是分割輪替要解的問題，
而觸發它的是磁碟用量曲線，不是這裡的 tps。

### 已知不在這個數字裡的

* **RLS 的成本** —— 兩輪都用平台情境。要量 RLS 是另一個 A/B（`fms_app` vs
  平台情境），而它會是完全不同的比例。
* **實際的工單路徑** —— 這裡改的是 `assets.updated_at`。真實的
  `transition_work_order` 還會寫 `work_order_transitions` 與 outbox 事件，
  所以絕對延遲更高；但**稽核那一段的比例**是同一個機制。
* **並發放大** —— 4 個客戶端。`audit_log` 是按月分割的，同一個分割會是
  寫入熱點；更高並發下比例可能變差。

## 250 人同時在線的容量量測（2026-08-04）

客戶給定的目標規模：**250 人同時在線、100 間教室、1000 台裝置、200 張工單**。

夾具是 `sql/076`（`MIGRATE_MODE=scale`），負載由 `cargo run -p fms-loadtest
--release` 施加。兩者的說明都在各自的檔頭 —— 這裡只記結果與怎麼讀它。

### 目標規模的解讀（寫下來，因為它影響每一個數字）

* **1000 台裝置**建成 `fms.devices` + 每台一個 `telemetry_points`，
  不是 `assets`。理由是壓力測試需要 `telemetry:batch-ingest` 有 1000 個
  真實的目標點，而那是寫入量最大的一條路徑。
* **200 張工單是資料量，不是吞吐目標。** 200 列對查詢規劃器是一個可以整表
  掃完的小表 —— 因此下面的延遲反映**併發與排隊**，不是索引在真實資料量下的
  效率。要量後者需要 10 倍以上的資料，那是另一次量測。
* 混合比例（每 100 次操作）取自校園作息，不是均勻分佈：
  行事曆 30、我的工單 20、佔用地圖 15、可用時段 10、建立預約 8、
  打開工單 7、儀表板 5、遙測上傳 5。

### 結果：連線池大小的 A/B

同一份 60 秒負載，唯一的變數是 `DB_MAX_CONNECTIONS`。

| | 10（預設） | 50 |
|---|---|---|
| 整體吞吐 | 636 req/s | **791 req/s** |
| `reservations:list` p50 / p95 | 380 / 456 ms | **275 / 335 ms** |
| `occupancy` p50 | 383 ms | **277 ms** |
| `dashboard` p50 | 397 ms | **341 ms** |
| `telemetry:ingest` p50 | **480 ms** | 636 ms |
| `telemetry:ingest` max | **713 ms** | 2,945 ms |
| `reservations:create` p95 | **466 ms** | 771 ms |
| `reservations:create` max | **540 ms** | 1,999 ms |
| 250 人同時登入 p50 | 1,016 ms | **643 ms** |
| 錯誤 | 0 | 0 |

**讀變快 24%，寫的尾巴變差 3–4 倍。** 預設的 10 條連線並不是一個「太小」的
設定 —— 它在當**入場管制**：連線池把並發擋在資料庫外面，於是寫入路徑
（排他約束、遙測分割表、稽核觸發器）不會互相踩。放大到 50 之後更多寫入
同時抵達資料庫，競爭從應用層搬到了資料庫層，而尾端延遲爆掉。

**建議：讀多寫少的部署可以調到 20–30；不要在沒有量測的情況下往上調。**
真正該做的是把讀寫分到兩個池，而那是一個設計變更，不是調參數。

### 一個訊號：所有操作的延遲幾乎一樣

10 連線那一欄，`dashboard`（一次請求回傳整個場域的彙總）與
`reservations:list`（一次索引掃描）的 p50 差不到 5%。

**那是排隊的特徵，不是查詢成本的特徵。** 用 Little's law 反推：
636 req/s × 0.38 s ≈ 242 個請求同時在飛，而池子只有 10 條 ——
每個請求真正的資料庫工作約 16 ms，其餘約 364 ms 在等一條連線。

50 連線那一欄，各操作的延遲開始分化（`dashboard` 341 vs `list` 275），
也就是說瓶頸從排隊移到了查詢本身。**兩欄一起看才看得出瓶頸在哪。**

## 發現一：登入會餓死所有其他請求（真缺陷）

**量法**：一邊跑 60 秒穩態負載，一邊在第 20／40／55 秒各注入一次
「250 人同時登入」（`LOAD_LOGIN_ONLY=1`）。唯一的變數是有沒有那三次風暴。

| | 無風暴 | 有 3 次風暴 |
|---|---|---|
| p50 | 380 ms | 400 ms |
| p95 | 456 ms | 505 ms |
| **p99** | **500 ms** | **1,717 ms** |
| **max** | **535 ms** | **1,844 ms** |
| 登入自己的 p50 | 1,016 ms（空機） | 2,700 ms |

**八個操作的 p99 全部落在 1,716–1,745 ms**（遙測 1,819）。
`occupancy` 是這組裡最輕的一支讀取，它與 `dashboard` 受到的懲罰一模一樣。

**齊一的懲罰代表被卡住的是共用資源，不是各自的查詢。** 那個共用資源是
tokio 的 worker 執行緒：`fms_identity::password::verify` 直接在 async
handler 裡呼叫（`handlers.rs` 的 token 路徑），而 argon2id
（m=19456, t=2）是**數十毫秒的純 CPU**。這台機器 10 核，250 次驗證
≈ 25 批 × 每批數十毫秒 —— 那段時間裡沒有任何 worker 在處理別的請求。

真實情境就是「早上八點 250 個人同時打卡登入」，而那一刻**整個系統的
p99 變成 3.4 倍**。

### 修法一（`spawn_blocking`）—— **不夠，實測只改善 8%**

把 argon2 包進 `tokio::task::spawn_blocking` 之後重量：p99 從
1,717 ms 只降到 1,576 ms。

原因：tokio 的 blocking 池預設 **512 條執行緒**，而機器只有 10 核。
250 個 argon2 任務各拿到一條執行緒，然後**一起搶那 10 個核**。
瓶頸從「tokio worker 被佔住」變成「CPU 被佔滿」，async worker 同樣拿不到
CPU —— 只是換成被 OS 排程器餓死。

`spawn_blocking` 解決的是「runtime 完全無法前進」，
**CPU 飽和要用入場管制解決**。

### 修法二（有界並發）—— 這個有效

加一個信號量，把 argon2 的並發限制在**核數的一半**
（`ARGON2_MAX_CONCURRENCY`，這台機器上是 5）。登入因此排隊，
而不相關的請求拿得到 CPU。

同一份實驗，`DB_MAX_CONNECTIONS=10`，全部在同一天同一台機器上量：

| | 無風暴 p50/p95/p99 | 有 3 次風暴 p50/p95/p99 | 有風暴的吞吐 |
|---|---|---|---|
| **修正前** | 380 / 456 / **500** | 400 / 505 / **1,717** | 572 req/s |
| 只加 `spawn_blocking` | —— | 391 / 495 / **1,576** | 597 req/s |
| **加有界並發** | 344 / 409 / **461** | 321 / 367 / **1,362** | **724 req/s** |

風暴期間：**吞吐 +27%、p95 −27%、p99 −21%**，而登入自己也從
2,700 ms 降到 2,110 ms —— **沒有取捨，所有人都變好**。
減少 CPU 爭搶對每一方都有利。

### 但它沒有消除這個效應，說清楚

相對的傷害幾乎沒變：修正前風暴讓 p99 變 3.4 倍，修正後是 3.0 倍。

因為 **250 次 argon2 驗證本身就是約 1.2 秒的 CPU 工作**
（250 × 約 25 ms ÷ 5 個 slot）。那段時間有一半的核在算雜湊，
尾端延遲一定受影響。這不是 bug，是 argon2 的成本。

要再往下壓只有三條路，都不是程式碼問題：
* **錯開登入** —— 前端不要在同一秒重試；SSO 之後這件事由 IdP 承擔。
* **少登入** —— access token 15 分鐘、refresh 7 天，客戶端該用 refresh
  而不是重新輸入密碼。**這是最有效的一條。**
* **更多核** —— 這個效應與核數成反比。

### 執行間的變異約 7%

`修正後／無風暴` 的 p50 是 344 ms，而 `修正後／有風暴` 是 321 ms ——
後者「更快」。**那是雜訊，不是結果。** 同一台開發機上重複量測的變異
約 7%（背景程序、熱節流）。

因此只有**超過那個幅度**的差異才算數：p99 的 1,717 → 1,362（−21%）
與吞吐的 572 → 724（+27%）都遠超雜訊；p50 的 344 vs 321 不算。

## 發現二：教職員看不到哪間教室是空的（權限資料）

`GET /facilities/{id}/availability` 要 `reservation:read`
（`fms-reservation/src/handlers.rs`），而 **REQUESTER 沒有那個權限** ——
它有的是 `reservation:read_own`。

也就是說一個老師可以 `reservation:create`，卻查不到任何教室的空檔，
只能盲訂然後吃 409 `RESERVATION_CONFLICT`。

這是負載測試的副產品：把 `availability` 掛在教職員角色上時，
那一格 100% 是 403。**403 是正確的授權行為，錯的是權限資料。**

不是這一刀修的東西（改的是 008 的 `role_permissions`，而
「教職員該不該看到別人在哪間教室、什麼時段」是產品決定 ——
私人預約的遮罩已經在，所以風險比看起來小）。負載腳本目前把
`availability` 送給場域管理員，並在程式碼註解裡標明那不是真實角色。

### 250 人容量量測（上方第二節）

| | |
|---|---|
| 夾具 | `MIGRATE_MODE=scale make migrate`（`sql/076`）|
| 指令 | `cargo run -p fms-loadtest --release`（**必須 `--release`**）|
| 參數 | `LOAD_USERS=250`、`LOAD_SECONDS=60`、`LOAD_INGEST_BATCH=20` |
| 伺服器 | `cargo build --release -p fms-server`，本機 `127.0.0.1:8080` |
| 資料庫 | `fms`（開發庫），PostgreSQL 在 compose 裡 |
| 日期 | 2026-08-04 |
| 機器 | 開發用 macOS，**10 核**（核數是關鍵：發現一的效應與它成反比）|

**每次量測前要重跑 `sql/076`。** 它會刪掉負載帳號名下的預約 ——
時段空間是有限的，不重設的話第二次執行會撞到第一次留下的資料，
而 `reservations:create` 那一格就變成在量衝突處理（實測 11.3% 的 409）。

**負載工具會判定這次量測有沒有意義。** 任何操作的錯誤率超過 2% 時它印出
警告並以離開碼 2 結束。這不是防禦性程式碼：第一次執行時 8 個操作有 5 個是
100% 錯誤（403／404／422／400），而報告顯示「整體 1,293 req/s、p50 0.1 ms」
—— 每個數字都是真的，整份報告的意義是零。**錯誤路徑當然快：
它們在碰到資料庫之前就返回了。**

修好那五個操作花了五輪，每一輪的原因都不一樣，而且沒有一個是效能問題：

| 症狀 | 真正的原因 |
|---|---|
| `reservations:list` 全部 400 | `to_rfc3339()` 產生 `+00:00`，query string 裡的 `+` 被解成空白。要用 `Z`（前端一樣會踩）|
| `availability` 全部 422 | 參數是 `from`/`to` 與 `resource_ids`（複數），不是 `date`/`resource_id` |
| `occupancy`／`dashboard` 全部 403 | REQUESTER 沒有 `reservation:read`／`report:read` —— **正確的授權行為**，錯的是負載模型 |
| `wo:available-actions` 全部 404 | 技師只有 `work_order:read_own`，別人的工單一律不存在。要用**每個技師自己的**工單清單 |
| `reservations:create` 404「resource is not bookable」| `resource_id` 是**底層節點的 id**，不是 `bookable_resources.id`。清單端點同時回兩個欄位 |
| `reservations:create` 77.6% 409 | 資源的 `buffer_after_minutes = 10`，所以 50 分鐘的預約實際佔用 60 分鐘 —— 10 分鐘的步進必然重疊 |

腳本有兩個防空轉檢查，都是實測踩過之後加的：

* **B 階段必須真的沒有寫稽核列。** 否則 `DISABLE TRIGGER` 沒生效，
  兩個數字會幾乎相同 —— 那會被誤讀成「稽核幾乎免費」。
* **A 階段的稽核列數必須 ≥ 交易數。** 第一版的 UPDATE 寫的是
  `name = name || 'x'`，而 `assets.name` 是 `varchar(200)`：約 180 筆之後就
  超長，A 只成功 769/1000、B 一開始就全滅。那一版量的是「append 幾次會爆掉
  varchar(200)」。**一個會隨執行次數改變行為的基準不是基準。**
