# ADR-10　工時成本與 chargeback 的前置決策

| 項目 | 內容 |
|---|---|
| 狀態 | **暫緩實作**（等待業務決策；技術上無阻礙） |
| 日期 | 2026-07-31 |
| 相關 | 規格書「未納入」清單、`work_order_labor`、`quota_policies`、ADR-04（資料庫為最終權威）、docs/WBS-rebaseline.md 4.1m |

## 摘要

工時**分鐘數**已實作並可用；工時**成本**刻意未實作，`labor_cost` 恆為 0、
明細的 `cost` 恆為 null。本 ADR 記錄這個決定的依據，以及日後要實作時
**必須先由業務回答的五個問題** —— 它們決定資料模型的形狀，選錯之後難以更改。

## 背景：為什麼算不出來

`hourly_rate` 這個欄位只出現在 `fms.work_order_labor` 自己身上。
全 schema 沒有使用者費率表、沒有技能費率表、沒有團隊或班別費率表，
`openapi.yaml` 的 `WorkOrderTransitionRequest` 也沒有 rate 欄位。

也就是說：**費率沒有來源**。要算成本，只能由呼叫端每次傳一個數字進來，
或由應用層憑空假設一個預設值。

## 決策

**不實作工時成本，且不填預設費率。**

`labor_cost` 保持 0、`work_order_labor.hourly_rate` 與 `cost` 保持 NULL。

### 理由一：規格書明確排除

規格書把「費用結算與計費（Chargeback）」列在未納入項目，並兩次說明
欄位已預留（`is_chargeback`、`chargeback_org_id`）而出帳流程未實作；
`chargeback` 亦與 BI、行動端一同列在 Phase 1 之後。

工時成本不是獨立議題 —— 單價 × 工時就是出帳的計算基礎。
現在補一個費率模型，等於把規格書刻意排除的範圍做一半，
而真正的 chargeback 設計進來時很可能得推翻它。

目前的行為正好對應規格書的敘述：**欄位在，值誠實地是空的。**

### 理由二：假的精確比留空更糟

填一個預設費率會產生**看起來精確而實際憑空**的成本數字。
它會流進報表、被拿去做決策，而沒有人知道它是假的。
NULL 至少會在第一次有人要用它時就被發現。

這與本專案在別處的一致立場相同：資料庫的 `TEXT + CHECK` 不驗證值時，
應用層擋在前面回 422，而不是收下一個看起來合理的錯值
（見 WBS-rebaseline 4.2）。

### 理由三：這是業務決策，不是技術決策

見下節。程式碼與 schema 都無法回答那些問題。

## 實作前必須回答的五個問題

| # | 問題 | 為什麼影響資料模型 |
|---|---|---|
| 1 | 費率依**使用者**、**技能**、還是**班別**？ | 決定費率表的主鍵與掛載點。依技能則需與 `maintenance_templates.required_skill_codes` 對齊；依使用者則掛 `users`。 |
| 2 | 加班倍率固定還是依合約？ | `work_order_labor.is_overtime` 目前是 boolean。若倍率依合約而異，這個欄位不足，需要「適用哪份費率規則」的參照。 |
| 3 | 外包與員工同一套嗎？ | 002 已有 `CONTRACTOR`／`VENDOR`／`SERVICE_ACCOUNT` 等 `user_type`。外包多半以工單計價而非工時計價，那是不同的計費模型而不是不同的費率值。 |
| 4 | 跨租戶／跨場域是否不同費率？ | 決定費率表要不要 `facility_id`，以及 RLS 政策與 `facility_scope` 的關係（見 WBS-rebaseline 4.1f）。 |
| 5 | 幣別如何處理？ | `work_orders.currency` 目前可為 NULL，`parts.currency` 亦然。跨幣別的租戶需要決定換算時點（發生時／出帳時）。 |

**問題 1 與 3 是最關鍵的**：它們決定的是「計費模型」而不只是「費率數值」，
兩者選錯之後的遷移成本差一個量級。

## 一個已經定案、可直接沿用的模式：成本在發生時快照

料件成本已經實作，做法是**在領用時把單價與總額寫進 `work_order_parts`**，
而不是每次讀取時去 join `parts.unit_cost`：

```sql
-- fms-workorder::repo::record_part_usage
SELECT ..., p.unit_cost, p.unit_cost * $qty, ...
FROM fms.parts p WHERE p.id = $part_id
```

理由是**日後調價不該改寫已完成工單的成本**。工時面臨完全相同的問題
（調薪不該改寫上個月的工單），因此費率設計必須在兩種做法中明確選一個：

* **快照**（與料件一致）：工時列寫入時把當時費率與成本一併存下。
  簡單、與既有模式一致；代價是費率填錯時無法回溯修正，只能逐列改。
* **版本化費率表**（`valid_from` / `valid_until`）：成本在讀取時依
  工時發生時間查對應版本。可回溯修正；代價是每次讀取都要 join 時間區間，
  而且要處理「費率表有空隙」的情況。

**建議傾向快照**，理由是它與料件一致，而「一致」在成本計算這種會被稽核的
領域比「可回溯修正」更有價值 —— 兩種來源用兩種模式，對帳時很難解釋。
但這仍需業務確認「費率填錯後如何處理」的實務做法。

## 與既有機制的交互

實作時必須一併考慮，否則會出現兩套帳：

* **`is_chargeback` / `chargeback_org_id`**：工單層級已有這兩個欄位，
  且 `PATCH /work-orders/{id}` 已可設定。出帳流程進來時，
  成本計算必須以它們為分攤依據。
* **`quota_policies` 與配額帳本**：規格書描述配額的計量方式包含「金額」，
  且帳本要能「回溯到具體預約」。若軟性服務的工時成本要計入配額，
  兩者的金額定義必須一致，否則同一件事會有兩個數字。
* **`recompute_costs`**：現行實作**由明細列重算**而非累加
  （累加在重試後會漂移）。費率進來後這個函式是唯一需要改的地方，
  這是刻意的設計 —— 成本計算只有一個入口。

## 現在就已完成、不需重做的部分

* `work_order_labor` 明細列（使用者、起訖、分鐘數）已寫入
* `labor_minutes` 由明細 rollup，與明細之和永遠一致
* `include=labor` 已可讀取，`cost` 欄位已在契約中宣告為可為 null
  並註明原因
* `recompute_costs` 已是唯一的成本計算入口

**費率進來後要改的只有兩處**：`record_labor` 填入費率與成本、
`recompute_costs` 的 `labor_cost` 加總會自然生效。

## 後果

* Phase 1 交付的工單有正確的工時**分鐘數**與料件**成本**，沒有工時成本。
  任何以工單總成本做決策的報表都必須知道這一點。
* 若客戶在 Phase 1 就要求工時成本，這是**範圍變更**，
  需先回答上節五個問題，並獨立估算（不在原 494 人日內，
  因為規格書本就排除）。
* 本 ADR 的存在本身是交付物：下一個團隊不需要重新發現這些問題。
