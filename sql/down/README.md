# Down migrations

## 範圍：只涵蓋 014 以後

`001`–`013` **刻意沒有** down migration。

那些是規格書交付的基線 schema：建立 98 張表、RLS 政策、狀態機、種子資料。
「回退」它們的意思是把資料庫變成空的，而那不是任何人在生產環境會做的操作
—— 真正的做法是**從備份還原**（`make restore DUMP=…`）。
為建庫腳本寫 down migration 會產出一份永遠不會被執行、
因而也永遠不會被驗證的程式碼，那比沒有更危險。

需要可逆的是**增量變更**：014 之後每一個 migration 都有對應的 down。

## 一個 down migration 該還原什麼

分成三類，處理方式不同：

| 類型 | 例子 | down 要做的事 |
|---|---|---|
| **結構** | 新表、新函式、新政策 | `DROP` / 還原成前一版定義 |
| **設定資料** | catalog 種子（015 動作標籤、017 型錄、018 料件） | 刪除本 migration 插入的列 |
| **示範資料** | 019 的服務帳號 | 刪除，但**先檢查有無外部參照** |

**不還原業務資料。** 例如 018 建了料件，若已經有工單領用過它們，
down 會因外鍵 `RESTRICT` 而失敗 —— 這是**正確的**：
還在被引用的資料不該被靜默刪掉。down migration 失敗並說明原因，
比留下一個指向不存在料件的工單好。

## 用法

```sh
make migrate-down TO=016    # 回退到 016（執行 021、020、019、018、017 的 down）
```

逆序執行，且每一步都在自己的交易裡：一步失敗不會讓前面成功的步驟回滾，
狀態仍然是明確的（停在某個版本，而不是半個版本）。

## 驗證

`make migrate-roundtrip` 在一個拋棄式資料庫上跑「全部 up → down 至 013 → 再 up」，
並斷言最終的**物件簽章**與第一次 up 之後完全相同：表與檢視、欄位（名稱／型別／
可空性）、約束定義、函式定義的 md5、政策的判定式。

比對簽章而不只是數量，是因為「數量相同但內容不同」很容易發生 ——
函式定義被換掉、主鍵欄位變了，數量都不會動。

CI 會執行它（`data-layer` job 的最後一個步驟）—— 沒有被執行過的 down migration
等於沒有 down migration。它跑在拋棄式資料庫 `fms_roundtrip` 上，
不影響同一個 job 前面的任何檢查。
